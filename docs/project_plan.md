# 프로젝트 계획

## 목표와 현재 우선순위

날짜×센터 단위의 다음 날 유입 BOD, T-N, T-P 예측 파이프라인을 재현 가능하게 만든다. 현재는 모델 학습보다 다음 작업을 우선한다.

1. 서울시 수질·처리량 API의 페이지 수집, 재시도, 캐시, 재개
2. API와 사용자 보유 CSV의 스키마·행 수·값 대조
3. 센터·처리장·계통 구조 및 `구분없음`의 의미 검증
4. 결측·0·이상치 후보 규칙과 시간 누수 방지 검증

## 단계

### 1. 설계 및 구현 기반 — 진행 중

공식 API 명세, 데이터 사전, 품질 규칙, 센터 통합 관문을 문서화하고 합성 데이터 테스트를 작성한다.

### 2. 실자료 확보·품질 검증 — 입력 대기

API 원문을 페이지 단위로 보존하고 체크포인트·조회 조건·해시를 기록한다. CSV는 CP949로 읽어 API 결과와 대조하되 최종 데이터 원천으로 사용하지 않는다.

완료 기준은 센터·처리장·계통별 기간, 빈도, 중복, 결측, 0, 이상치 후보, 단위 및 병합 손실이 실제 자료로 보고되는 것이다.

### 3. 센터 일별 통합

공식 구조 또는 데이터 기반 보존식이 확인된 규칙만 적용한다. 산술평균은 기본 금지하며, 처리량 가중도 수질 값과 유량의 대응 관계가 확인된 경우에만 허용한다.

### 4. 특징·검증 데이터셋

예측일보다 이전인 7·14·30일 창을 만들고 기본 14일을 사용한다. 모든 변환기는 학습 구간에서만 적합한다.

### 5. 모델 비교

지속성·전일·전주 계절 기준모델을 먼저 평가한 뒤 LightGBM, XGBoost, LSTM을 동일 평가행에서 비교한다. 이 단계는 실자료 검증과 통합 규칙 확정 전 시작하지 않는다.

## 폴더 책임

- `src/data/`: API 요청, 원문 캐시, 재개
- `src/preprocessing/`: 스키마, 품질 요약, 센터 통합 관문
- `data/raw/`: 변경하지 않는 API 원문과 제공 CSV
- `data/processed/`: 재생성 가능한 정규화 자료
- `reports/`: 품질·검증 결과
- `tests/`: 페이지, 스키마, 누수, 통합 규칙 검사

## 완료 관문

API 키와 원자료가 없으면 실자료 완료를 주장하지 않는다. 데이터 가용 시작일이나 센터 구조가 기준안과 다르면 모델을 먼저 만들지 않고 분할·통합 설계를 갱신한다.


## 현재 단계 갱신(2026-11-11)

처리량 합산은 공식 정의가 미확인되어 1차+2차 계산 가설과 원 성분을 함께 보존하는 단계까지 구현했다. 센터 농도 통합은 난지·탄천·서남의 처리장 구분없음을 조건부 직접 사용 후보로, 중랑은 처리장별 예측 대안으로 유지한다. 모델 학습은 수행하지 않았다.

다음 단계는 API 키와 시설 메타데이터 확보 후 CSV-API 대조, 처리량 비중복성 및 채수 경계 확인, ASOS 실자료 결합이다. 공식 근거가 확보되기 전 센터 합계나 유량가중 농도를 확정하지 않는다.
